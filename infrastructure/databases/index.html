    PostgreSQL, Prisma, Citus and CNPG¶

    PostgreSQL and Prisma¶

    What is it? PostgreSQL is the relational database; Prisma supplies typed queries and versioned SQL migrations. A schema describes tables and constraints.

    Why Clichy uses it Users, sessions, photo metadata and outbox events need consistent transactions. Image bytes remain on the photos volume.

    Schemas and immutable migration history live in packages/db/prisma. Use prisma migrate dev locally and prisma migrate deploy for deployed environments, through the documented entry points. Never edit an applied migration or replace its history with db push.

    Citus: Test photo metadata¶

    What is it? Citus extends PostgreSQL with distributed/reference tables. A distribution key selects a hash shard; colocated tables share shard placement.

    Why Clichy uses it Test demonstrates logical sharding by user, keeping a photo and its processing outbox colocated. Production and Dev do not use Citus.

    flowchart LR
  App[Test API and worker] --> Citus[One Citus Pod / clichy-citus-rw]
  Citus --> User[user: reference table]
  Citus --> Photo[Photo: hash userId / 32 shards]
  Citus --> Outbox[PhotoProcessingOutbox: hash userId / 32 shards]
  Photo ---|same colocation ID| Outbox
  Citus --> PVC[(One data PVC on valtask)]

    The pinned citusdata/citus:14.2.0 image initializes its own extension on a fresh volume. No repository init/repair ConfigMap is needed. Migration 20261117130000_register_citus_sharding owns registration: it only acts in clichy_test, requires the extension, creates missing registrations and checks the expected layout in one transaction. Existing correct shards are left intact; incorrect existing registrations fail without automatic conversion. Future sharding changes belong in new migrations, not a second post-deploy SQL mechanism.

    user is a reference table (n/t, one shard); Photo/outbox use hash(userId), 32 shards each and the same positive colocation ID. Primary/unique keys include userId; the outbox FK is (userId, photoId) -> Photo(userId, id). Photo-to-user delete is RESTRICT, outbox-to-photo delete is CASCADE; both updates are RESTRICT, since shard keys are immutable. Application jobs/queries carry userId.

    This is one PostgreSQL process on one host, not multi-node scale-out or HA. The healthcheck checks layout and FKs without executing migrations. For detailed metadata inspection:

    kubectl exec -i -n clichy-test deployment/clichy-citus -- \
  env PGOPTIONS='-c default_transaction_read_only=on -c statement_timeout=10000' \
  psql -X -U clichy -d clichy_test <<'SQL'
SELECT logicalrelid::regclass, partmethod, repmodel, colocationid,
       CASE WHEN partmethod = 'h' THEN column_to_column_name(logicalrelid, partkey) END AS key
FROM pg_dist_partition;
SELECT logicalrelid::regclass, count(*) FROM pg_dist_shard GROUP BY logicalrelid;
SQL

    A one-task EXPLAIN alone does not prove hash distribution. Scope routing queries by userId; inspect catalog metadata to distinguish local/reference registrations from hash shards.

    CloudNativePG: physical replication¶

    What is it? CNPG is a Kubernetes operator managing PostgreSQL primary/replica Pods and failover. PostgreSQL streams WAL (write-ahead log) to a standby.

    Why Clichy uses it Dev/Production use its primary Service directly, while Test retains a separate CNPG cluster for replication exercises. CNPG does not replicate Test's Citus database.

    flowchart LR
  App[Dev / Production application] --> RW[clichy-postgres-rw Service]
  RW --> Primary[Primary Pod and PVC]
  Primary -->|Asynchronous WAL streaming| Replica[Replica Pod and separate PVC]
  Operator[CNPG operator] -. reconciles and promotes .-> Primary
  Operator -. supervises .-> Replica

    cnpg/cluster.yaml declares two PostgreSQL instances with preferred anti-affinity and asynchronous streaming (minSyncReplicas: 0, maxSyncReplicas: 0). Both run on the same host. Writes do not wait for standby acknowledgement, so failover can lose recent transactions. The operator updates the -rw Service after promotion; the app has no replica-read routing.

    Check live roles using kubectl get pods -n clichy-prod -l cnpg.io/cluster=clichy-postgres -L cnpg.io/instanceRole. On the primary, SELECT application_name, state, sync_state FROM pg_stat_replication; shows senders. The Production healthcheck observes a streaming standby; neither that observation nor Ready status demonstrates failover or zero data loss. The optional kubectl cnpg status command requires a separate plugin.

    Backups and limits¶

    There is no tested backup/restore automation. Database replicas, Redis AOF and PV Retain do not protect against accidental deletion or loss of valtask. A verified backup must coordinate PostgreSQL metadata with original/derivative files and be restored into an isolated target. Do not delete PVCs, redistribute existing tables or resolve failed migrations blindly. Historical repairs remain available in Git history rather than in normal deployment manifests.
